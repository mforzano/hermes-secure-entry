# Private manual verification-code fill

**Unreleased: do not activate with real codes.** Stock Hermes 0.23.2 can expose populated fields through later browser tools (see release blocker below).

`secure_entry_otp_fill` is a separate in-process tool for stock Hermes 0.23.2 in an authenticated Photon, Discord or Telegram DM with the plugin's tailnet-only private entry already configured. It uses neither the native OTP classifier nor a saved login, seed, or vault record. The manual and bridged native `browser_vault enter_code` routes share one attempt per authenticated owner and browser task in a turn. Manual entry spends it at native consent; the bridge spends it when the native code callback runs. A genuine `no_code_field` before handoff does not spend it. Refusal, cancellation, or an unknown write does not rearm it. Manager unlock, signup, and payment are not part of this guard.

1. Inspect the actual verification step on the task's captured Chrome browser. Read only field descriptors, labels, order, and backend node IDs, not values or DOM dumps. Supply the inspected `parent` page target, exact `frame` ID (root or direct iframe), `origin` of the top-level page, `frame_origin` of the OTP document, and `otp_nodes` (CDP `backendNodeId` integers). Use the same exact HTTPS origin for both on a root document. Select only the intended input or all inputs in one widget. Never pass selectors, code text, a handle, or a seed.
2. Native confirmation names both origins and the exact targets. After approval and revalidation, the plugin sends one one-use masked-code link through the existing native DM sender. It expires within three minutes. Do not resend it or paste codes in chat. The capability URL may appear in sent-message history; treat it as private. Use the form's Cancel button before handoff. Stop/reset/unload, loss of capture, and native human takeover also fence the operation.
3. `filled` means the selected controls held the exact expected values at native verification. It does **not** mean the site accepted the code or the account is signed in. The tool never clicks, presses Enter, or submits; the website may auto-submit in response to input events. `code_mismatch` means nothing was sent to the site. `write_unknown` means disclosure may already have occurred; inspect the site without reading or showing input values, and do not blindly start another attempt.

Supported shapes: one writable input recognized from OTP semantics, including an explicit label such as “Enter the 6-digit code”; a numbered split with complete, consistent positions `1..N`; or a classic `maxlength=1` run with OTP evidence. Split layouts require adjacent rendered controls with actual common form/container scope, not just matching names or missing form IDs. A malformed, incomplete, reordered, or mixed split is refused before prompting. The classic layout may use one OTP anchor with anonymous numeric boxes. Split and explicit digit-count codes require the exact number of ASCII digits; ordinary fields allow ASCII letters and digits within their length limits. Spaces and hyphens used as separators are stripped; leading zeroes are preserved. Unselected controls are not written.

The plugin reuses the native captured connection, retained document/nodes, desktop lease, approval and private broker. It does not retain a vault record or return the code from the fill tool. Stock WebSocket wire-debug tracing must be off. As with manual entry, page scripts and the browser endpoint can see a filled code. After final child readback, the tool checks the exact retained parent again. These checks are not atomic across documents; a post-dispatch loss of authority or response is not proof that nothing was written.

### Release blocker: later browser output

A synthetic run through the registered OTP tool and the actual stock `browser_exec` harness on isolated Chrome returned the split values as separate strings even though the joined code was redacted. In the native-vision path the attached screenshot changed when only the field values changed and returned to baseline after clearing them. No model request was made. Text redaction or CSS masking alone cannot protect both DOM reads and image output.

The generic tool-result transform sees output after execution, not the originating DOM nodes or the provenance of arbitrary browser-script output; a screenshot can also already exist as a file. Tool interception could refuse whole tools, but a task-only guard cannot isolate a shared CDP browser from other tasks or sessions. Neither is a narrow, fail-closed per-target egress control. Two paths need a separate scope decision: a host-enforced private-browser interval that excludes all model-facing access to the affected browser until safe release, or an explicitly consented private completion flow that owns the verification action and handles rejected or ambiguous outcomes without handing populated controls back. The existing fill-only tool authorizes neither submission nor broader access restrictions.

Synthetic coverage uses actual registered dispatch, Chrome/CapturedCDP, the native approval queue and Discord sender (network replaced), and the real one-use HTTP form on pristine upstream `v0.23.2`. It does not establish a live DM or live website acceptance for this tool.
